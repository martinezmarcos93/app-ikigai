# Handoff 10/11/2026 — login caído por HTTP 429

## Qué pasó
El portal mostraba «La API devolvió una respuesta no válida (HTTP 429)» al iniciar sesión. No era la API: el Cloudflare **de Render** devolvía su desafío anti-bots («Just a moment...», `cf-mitigated: challenge`) a los pedidos hacia `api.ikigai-training.com`. Por `ikigai-api-q17j.onrender.com` la API respondía bien. El 07/11 había pasado lo mismo con la otra dirección. Se levantó solo en minutos. El cron de cobros de las 09:00 llegó (confirmado por Marcos).

## Qué se hizo
- PR #47 (`7324bd0`, en producción como Worker `e7ec5c0a`):
  - el Worker prueba `API_ORIGIN` y, ante desafío, fallo de conexión o 520–530 de Cloudflare, reintenta el mismo pedido por `API_ORIGIN_FALLBACK`; un timeout no se reintenta;
  - todo bloqueado → `503 api_blocked` en JSON;
  - `ALERTA api:` en los logs, cabecera `x-ikigai-api-route: fallback`;
  - crons con `User-Agent: IkigaiWorker/1.0`; ping cada 12 min.
- Verificación: 18/18 tests del Worker; en Cloudflare real, versión al 0 % con override y la principal rota a propósito → el login pasó por el respaldo.
- Monitores UptimeRobot (Marcos): «Ikigai – login usuarios» (keyword `"status":"ok"` en app.) e «Ikigai – API principal» (api.), cada 5 min, mail probado.

## Aprendido
- Cloudflare devuelve **530** (error 1016), no una excepción, cuando un Worker no puede llegar al origen.
- `wrangler versions deploy` admite como máximo 2 versiones a la vez; para probar sin tráfico: versión al 0 % + cabecera `Cloudflare-Workers-Version-Overrides: ikigai-app="<id>"`.
- La credencial OAuth de wrangler no puede consultar la API de observabilidad (Forbidden): los logs se ven en el panel.
